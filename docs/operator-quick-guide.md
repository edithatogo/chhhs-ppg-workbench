## Walk through the completed PPG example

Use the completed fictional review and its separate next review. Keep any real
policy record read-only during the demonstration. The implementation owner supplies
the currently qualified form links and handles technical references; operators
should not have to assemble private flow bindings.

| Step | What to open or do | What the system retains |
| --- | --- | --- |
| Find the PPG | **Find a policy** → source Catalogue. Confirm the document and captured source/version. | Source identity and provenance, separate from local review work. A captured copy is not proof of current authority. |
| Open its review | **Open a review** → the fictional Review Queue item. Read the intended outcome, next action and proposed/accepted ownership. | A distinct review occurrence. Offering a role does not accept it; acceptance has its own record. See [initiation](lifecycle-operator-initiation.md). |
| Prepare and consult | Follow the case's **Open draft and evidence** link. Inspect the maintained-template Word draft, saved human edit, consultation and readiness records. | The selected draft revision, source/template provenance and version-scoped findings. Changed content requires new scoped findings. See [preparation and assurance](decision-implementation-assurance.md). |
| Record the decision | Open **Decision and implementation evidence for this case** and inspect the separate decision-purpose records and their evidence. | Explicit outcomes, reasons, conditions and next actions. Missing or adverse findings do not become approval. See [decision outcomes](lifecycle-operator-decisions.md). |
| Issue, implement and verify | Inspect the isolated fictional issued copy, its publication evidence, implementation record and separate verification finding. | Exact issued revision and evidence relationships. The copy is a technical example, not publication through the real policy channel. See [implementation and verification](lifecycle-implementation-verification.md). |
| Close and return for review | Inspect the completed case and its separate next occurrence. Compare the retained date/rule evidence and proposed ownership. | Completed history remains intact. The next occurrence is new work, with no inherited acceptance or approval. Demonstration dates are fictional, not a selected operational review interval. |

The demonstrated document route uses the maintained-template manual fallback,
SharePoint storage and Word on the web editing. Preferred SharePoint structured
document generation still needs exact production qualification before replacing
that route. Bounded failed/inconclusive, partial-write reconciliation and pre-receipt
recovery paths have technical evidence. Recovery from every possible interruption
is unqualified; a successful recording alone cannot close a review.

When editing a maintained-template draft, change text within its fields. Replacing
an entire field can remove its content control. Check the saved document after
closing and reopening it. If structure changes, retain that copy and prepare a
separate revision that carries the edits forward; do not overwrite the history.

## One retained example, five tasks

Use the retained unapproved example without changing its source, review findings
or business decisions. A maintainer may demonstrate recording with isolated
fictional inputs; viewing a real case is not permission to perform its review.

| Task | Operator steps | Check before continuing |
| --- | --- | --- |
| Find evidence | Start Here → Guides and tools → Captured policy archive — reference copies (or Find a policy for the source Catalogue). Open the captured file read-only. Use “download the full archive index (CSV)” and match its hosted filename to find source URL, capturedAt, hash and contentStatus. | Check captured date, version and authority label; a captured copy may be unconfirmed. |
| Find the case | Start Here → Open a review (Case workspace view). Open the retained example title. Read the grouped Case and source context, Proposed work, Review recording and Evidence and implementation records; follow its existing draft link. | Match case/document identity and source snapshot. Proposed roles and pending dates remain pending. |
| Prepare a package | Download the existing submission assembler; open the downloaded HTML locally. Enter recorded metadata, select actual files, assign categories and check completeness. Download a new DRAFT ZIP. | Follow the maintained [assembly steps](submission-package-assembly.md). Missing evidence remains visible. Downloaded utility use is manual; it is not a cloud action. |
| Record review work | Open the case’s “Readiness findings for this case”, “Decision and implementation evidence for this case” or “Consultation and ownership acceptance for this case”. Check the applied CaseUID filter. Read the maintained recording guides before recording any actual finding. | See [readiness](human-readiness-recording.md), [assurance](decision-implementation-assurance.md) and [handoff](consultation-handoff.md). Actual findings, role acceptance and approval require human work. A case edit is not an approval. |
| Find an earlier version | Use the file’s More Actions menu → Version history. If a hover card covers the menu, press Escape, then use the menu. Inspect the prior version and date; download a separate copy if needed. | Preserve the current human-edited file. Viewing/downloading a prior version does not authorise restoring it over current work. |

The file preview’s Info pane can show empty authority/edition fields. Do not
fill those fields merely to complete this walkthrough. The archive index supplies
capture provenance; its source URL and capture date do not prove current authority.

For a read-only walkthrough, task4 means locating the fields, guide and existing
history. An empty filtered history means no event is recorded, not that review passed.
The history filter does not prefill a new event: verify CaseUID, document, exact
version/hash and evidence yourself. Record native event creation as unperformed; a local fictional validation
example must not be described as native recording proof.

## When something stops

| Situation | Safe next step | Maintained route |
| --- | --- | --- |
| Stale input/version | Retain the selected snapshot and output; re-read current identity/version. Prepare a new explicit revision when inputs differ. | [Package preservation](unattended-package-generation.md) |
| Identity hold | Open the delivered resolution path and gather same-document/new-identity evidence. Leave the last successful checkpoint unchanged until a legitimate decision is available. | [Identity triage](identity-triage.md) |
| Interrupted operation | Retain its run ID, receipt and partial output. Inspect that same operation before retrying; distinguish missing receipt from missing output. | Existing tool's recovery guide; do not start a second recovery implementation. |
| Access denied | Retain the exact target, operation and error privately; use the existing supported route or ask support to diagnose that boundary. | Do not change permissions, copy credentials or repeatedly retry an unchanged denial. |
| Need last accepted output | Find its completion receipt and compare exact output identity/revision/hash. A newer file or metadata check alone is not success. | [Operator handoff](operator-reviewer-handoff.md) and native version history |

Cloud packaging and full maintained-Word generation have separate qualification
and ownership. See the [full Word guide](full-review-word-generation.md) for their
scoped evidence and current invocation instructions. This lifecycle extension
retains its working manual preparation route. Generating a package does not change
content status.

## Read freshness before acting

Start Here distinguishes the effective state, freshness and retained state/reason.
Read the three AEST clocks separately: latest source check, last verified
reconciliation and status update. A recent check or status update does not prove
successful reconciliation. A held state preserves the last verified baseline;
follow its recorded next action rather than extending the identity ledger yourself.
Capability modes are separate from content approval. Dated Word/package Off
observations are historical evidence, not a fresh claim about current runtime state.
