# Recover role registers into separate targets

This restores the role-management records; it does not apply responsibility or
portfolio decisions. Keep the working bindings and current issued history intact.
Use the versioned evidence archive and existing qualified CLI client. Confirm the
exact account, site, target rights and five schemas before any native step. No new
consent, licence or permission is needed by the qualified fixture route; other
targets require their own access checks.

## Preserve and prepare

Export the four input registers and dated-snapshot register completely: schemas,
stable item keys, current values, every available version and nonhidden views.
Refuse continuation links, missing original history, duplicate keys or unexpected
schemas. Preserve source bytes and original platform provenance in a hash-verified
archive. Upload, download and verify archive CRC/member hashes before planning a
restore from those downloaded bytes. Do not treat a local ZIP alone as recovery.

The read-only planner produces version-ordered business payloads and a separate
original-platform mapping. Run from the repository root with private paths:

```sh
.venv/bin/python -m scripts.ppg_role_recovery \
  --input .local/recovery/source-export.json \
  --output .local/recovery/new-restore-plan.json
```

The command refuses an existing output file and makes no tenant writes. Current
support is the five known text/choice schemas and contiguous major item histories.
An evicted original, unsupported value or different schema needs reconciliation;
do not manufacture a missing history or silently omit it.

## Reconstruct and verify

Use separate, clearly named recovery Lists with versioning, the same field types,
required flags and unique stable keys. Keep them outside live bindings, search
indexing and quick-launch navigation. Retain inherited security; no ACL migration
or access grant is implied. A new list/item receives new platform identity and
audit stamps. Preserve the originals in evidence instead of writing them into
Created/Modified/Author/Editor or claiming audit impersonation.

Create each stable key once from its original business-field payload. Replay its
subsequent versions in order with exact current ETags. After each step read back
all expected fields and the version label/history. An existing final record must
compare exactly; refuse unexpected keys, extra versions or changed values. Never
reset a final or edited record to the original seed. Use a transport that prevents
mutation retries/redirects; the CLI's generic request retry is not an exactly-once
write guarantee. After an uncertain response, reconcile the actual key/history
and journal before another send.

Recreate view fields, queries, row limits, paging and defaults separately. Compare
all recovered business histories and original snapshot manifests. Prove equivalent
dated responsibility projections and recorded portfolio-transfer audit results.
A recovery copy of a dated snapshot retains its original source pins; do not
regenerate or repin it merely because the platform IDs changed.

Replay must produce zero record creates/updates and zero view/settings changes.
Fresh complete source exports must prove the working schemas, values, versions
and views unchanged. Retain the source-to-target mapping, first-run and replay
receipts, downloaded archives and any failed observation. Do not replace live
bindings as part of this exercise. A production recovery/cutover remains a
separate authorised operation with its own security and adoption checks.

No business decisions, notifications, source-register edits or policy issuance
