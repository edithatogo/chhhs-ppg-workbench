# Native operator verification

> Current workflow baseline: [versioned register and status reconciliation](workflow-documentation.md). Dated qualification sections below retain their original scope; read the current baseline before treating an earlier limitation as current.

The adverse-only route below is retained qualification history. The same existing
operator flow has subsequently been upgraded for a prepared implementation parent
and a seven-field form, including `Verified (recorded)`. Its corrected native
first-create and identical zero-create repeat are documented in
[lifecycle implementation and verification](lifecycle-implementation-verification.md#native-prepared-verification--18-october-2026).
That technical result does not grant closure or real effectiveness.

## Historical failed and inconclusive route

A native Power Automate form records fictional Failed or Inconclusive verification
findings against the selected implementation record and exact reviewed version.
The five inputs are event reference, outcome, method/finding, evidence reference
and next action. The current pilot is explicitly limited to one fictional case.

The flow validates supported inputs before reading the case. It checks case/source,
consultation and readiness pins, then reads the selected native Implementation
record and checks its exact scope, stage, recorded state and fictional marker.
The new Verification event references that implementation. It retains the entered
method, finding, evidence and next action, with open conditions and notes. No
completion is granted and the case is not advanced.

## Native verification

Both Failed and Inconclusive examples were entered through the actual browser run
form. Both native runs succeeded, and stored-event readback verified their results,
open conditions and exact implementation parent. They are parallel qualification
scenarios and do not supersede the separate successful verification example.

An attempted `Verified (recorded)` outcome through this adverse-outcome form failed
input validation. Case read and event creation were both skipped. The flow was
stopped after testing; native readback verified its state and accepted definition,
excluding only the service-injected authentication member.

Private exact definitions, run/action outputs and stored findings remain under
`.local/policy-lifecycle/lc04-operator-verification-*`.
`tools/lifecycle/build_verification_outcome.py` reuses the qualified decision-form
builder and exact fictional implementation readback to emit a stopped definition.
It rejects mismatched source scope or an unrecorded/nonfictional implementation.
It does not deploy or authenticate.

A focused local evidence-gate check also confirms that Failed and Inconclusive
verification cannot support review closure even if their conditions are mistakenly
marked resolved. All thirteen component checks pass. This supplements native
recording proof; native case-closure integration remains with the case writer and
has not been proved by the local check.

## Remaining work

General case selection, ordinary-user access and authority, native review-closure
refusal, identical/changed-input replay in this particular form, complete operator
navigation and full lifecycle acceptance remain open. This flow has only one
possible event create and no case/source/publication/assignment/notification or
permission mutation. These technical examples establish no real policy outcome.
