## Form and identity

| Field | Meaning |
|---|---|
| Request reference | An LC02-OP- reference identifies the complete submitted request. Reuse only for an identical retry. |
| Review occurrence reference | An OCC- reference identifies the review occurrence; the case identity is derived deterministically from it. |
| Intended outcome | What the fictional review should prepare. |
| Next action | What should happen next; no notification or assignment follows. |
| Proposed review role | A proposal, retained explicitly as UNACCEPTED. |

Text is trimmed consistently. Required fields, bounded lengths and safe reference
characters are validated before any source or case operation. Case identity does
not depend on a row number or title. Different request and occurrence references
serve different purposes: changing content under a retained request is refused;
a retained occurrence is read back, never silently overwritten by another request.

The flow verifies source metadata/content/metadata against the private exact pins.
It creates a retained request snapshot without overwrite, checks that its complete
request matches, then creates or verifies the occurrence in the existing Review Queue.
Source baseline points to that native request snapshot; document identity/version/hash
are retained in the snapshot. All case payload fields and a final source token are
checked before returning the native receipt. There is no case-update action.

The role is stored with an UNACCEPTED/proposed label, target date remains unset and
the case is explicitly fictional. Acceptance requires its own later evidence and
transition; initiating a case does not accept responsibility or approve policy content.
