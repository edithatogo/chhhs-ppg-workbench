# Operator handoff and usability evidence

Selected by the user on 17 October 2026 as an existing-permissions usability increment.

## Outcome

Deliver a short, reproducible operator walkthrough and recovery guide, reconcile
outdated documentation, and prepare proportionate measurement of actual friction.
Technical completion does not require doing substantive policy work or recruiting
reviewers. Real-use observations can follow after delivery.

## Deliverables

- A concise worked example covering discovery, case navigation, package preparation,
  review recording and locating the previous version. Label human review and manual
  operator steps explicitly; preserve the retained unapproved example.
- Recovery instructions for stale inputs, identity holds, interrupted operations,
  denied access and finding the last accepted output. Reference maintained tools
  and their receipts rather than inventing a second recovery implementation.
- Reconcile roadmap, feature guides and navigation with the registry: desktop
  acceptance closed by the user; core delivered; optional production/runtime gates
  open. Keep historical evidence clearly dated instead of rewriting old receipts.
- Reuse the existing process-measure dictionary and tools for task duration, missing
  inputs, help required and correction/rework counts. Specify denominator, as-of
  date and exclusions. Prepare a minimal optional observation sheet in the existing
  library; no new List, telemetry service, dashboard, schedule or respondent data.
- A short ranked follow-up list based on observed walkthrough friction. Real-use
  benefit and time saving remain unmeasured until actual comparable observations.

## Acceptance

Execute the guide using the supported route on retained read-only or isolated
fictional inputs; record steps, outcomes and help required. If a separate ordinary
user is unavailable, label it an operator walkthrough, not independent acceptance
or permission testing. Do not impersonate roles or change access to test them.
Verify hosted links/downloads and guide revision. Distinguish local simulation,
native proof and user acceptance. No re-opening the desktop walkthrough.

## Permissions and document route

Reuse existing guides/library and measure exports. For any new maintained Word
output, evaluate the preferred SharePoint structured-document route first; if an
actual prerequisite is unavailable, record it and retain the existing editable
format. No bespoke generator or dependency on the production Word track.
Measure the mechanism with fictional examples; collecting real business results
and substantive decisions remains later operational use, not a build blocker.

## Existing-permissions execution contract

Use [the shared permission and delivery contract](../../../docs/usability-delivery-plan.md).
Before a native change, read the exact existing target with the intended account,
record the available operation and preimage privately, and confirm its writer.
Recorded historical access is a starting point, not current operation proof.
Use only existing site/List/library rights and qualified clients. No tenant admin,
new consent/app registration, licence purchase/assignment, access changes, premium
runtime, new site, schedule or notification is required or authorised.
An unavailable operation takes its documented fallback; record the limitation and
continue independent tasks. Never call a fallback the unavailable native feature.
Preserve source fields, case decisions, original files, version history, unrelated
controls/views and inherited permissions. Native save/readback and repeat safety
are separate from local checks. No new deployment is claimed by this plan.
