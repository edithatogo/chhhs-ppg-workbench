# Project Workflow — value-first, limited ceremony

This is the project's deliberate customisation of the upstream workflow template.
The user's baseline scopes and selected follow-on plans are already supplied. Do not run setup,
ask another round of plan/phase approvals or import the template's >80% coverage
and mandatory TDD/checkpoint requirements. No global tool safeguards are disabled.

## Routine loop
1. Select one eligible registered task. Mark it `[~]`; set track metadata to
   `in_progress`. Inspect only the relevant context and exact target.
2. Produce the smallest useful output using existing tools. If native access is
   blocked, record the actual operation/error and continue independent preparation.
3. Verify the changed behaviour with a proportionate check/readback; retain
   detailed operational evidence privately and a sanitised summary in the handoff.
4. Mark `[x]` only for completed deliverables; record what is actually usable.
   Commit one coherent increment. One commit can include implementation and plan
   progress; no forced Git notes, separate ceremony or per-phase review panel.
5. Stop expanding when the track's stated output is usable. Report the next useful
   task. Do not add distant tracks or turn polishing into a hidden fifth MVP.

## Small checks that cannot wait
| Change | Minimum evidence before claiming it works |
|---|---|
| Context/configuration | Valid files, working links, intended field/pin values |
| List/library creation | Read back the intended resource/schema; no source edits |
| Snapshot import | Account for input and preserve original values/identity |
| Scheduled update | Repeat-run safety, row-move safety, local-edit survival and visible failure; commit checkpoint only on success |
| Template/sample package | Traceable inputs, preserved fields/status, editable output and working links; no source changes or inferred approval |
| Task/template automation | One actual representative output; repeat-safe behaviour if it creates records |

Do not substitute exhaustive tests for those direct checks. Wider performance,
accessibility coverage, CI, regression breadth and cross-service integration tests
are later hardening when scope warrants them. Do not defer critical data-loss,
confidentiality, source-write or false-approval defects. Stop the affected path,
not unrelated safe implementation.

## Permission without invented gates
Ordinary preparatory work and reversible pilot changes inside the identified
scope proceed under the user's instruction and actual permissions. A missing
required clinical sign-off, new external recipient, destructive action, new
spending, scope transfer or authentication challenge is resolved at that boundary.
Do not ask for approval to read known context, write drafts or complete each coding
phase. Do not treat non-response as clinical authorisation.

## Work in progress and blocked work
One template/sample-workflow increment and one automation increment at a time.
QW2 and QW3 are parallel; template demonstration does not depend on scheduled sync.
Substantive policy review is later operational use, outside this system build.
After two repeats of an unchanged tool failure, choose a supported alternative or
record the exact blocker and switch to independent useful work. Do not repeatedly
try credentials or keep investigating optional infrastructure.

## Context maintenance
Use `[ ]`, `[~]`, `[x]`; metadata statuses `new`, `in_progress`, `completed`,
`cancelled`. On completion, summarise observed output, evidence level, deferred
limitations and next action in `conductor/handoff.md`. Update the registry and
metadata together. Checked source code is not a deployed flow. Technical setup completion does not
establish content review or policy approval; those business states stay unperformed.

No future capability gets a detailed track until it removes a demonstrated task.
QW4 monthly reporting was explicitly selected by the user on 15 October 2026,
with policy evidence of monthly recurrence. It commissions only report preparation;
other candidate automations remain outside scope.

## Delivery coordination

Follow [delivery allocation, native ownership, inter-chat coordination and follow-on selection](delivery-coordination.md). Those instructions remain authoritative; existing writer assignments and authentication boundaries are unchanged.
